# 運用ランブック（C-Relations）

障害時・定期作業時に「何を見て、何をするか」をまとめた手順書です。構築手順は
[azure-deployment.md](azure-deployment.md)、仕様は [epc-task-graph-design.md](epc-task-graph-design.md) を参照。

> 連絡先（運用担当・Azure 管理者・承認者）はチームで決めて下の「エスカレーション」に記入してください。

---

## 1. 2 つの版と、データの置き場所

| | ローカル版（GitHub Pages・デモ版） | サーバー版（Azure） |
|---|---|---|
| データの場所 | **各ブラウザの IndexedDB**（端末・ブラウザ・URL ごとに別） | Azure SQL（全員で共有） |
| 同時編集 | 不可（同じブラウザで 2 つ目のタブは待機表示） | 可（行単位の衝突検知＋ポーリング同期） |
| 自動の保存履歴 | 直近 5 件＋日ごとに最新 1 件（最大 7 日分） | 同左（サーバー側）＋ Azure SQL の自動バックアップ（7 日） |
| 消える条件 | ブラウザの「サイトデータを削除」・端末の初期化・容量不足時のブラウザによる削除 | リソースグループ / DB の削除 |

**ローカル版で最も重要なのは JSON バックアップです。** IndexedDB は利用者の端末にしか無く、運用側から復旧できません。

## 2. 日常・定期の作業

| 頻度 | 作業 | 手順 |
|---|---|---|
| 毎週（ローカル版利用者） | JSON バックアップ | 「データ ▾ → JSONを書き出す」。共有ドライブ等、端末外に保存する |
| 毎週 | 依存更新 PR の取り込み | Dependabot の PR で CI が全て成功したものをマージ |
| 毎月（サーバー版） | 監視の確認 | Application Insights の「障害」で 5xx・例外の傾向を見る |
| 四半期 | **復元訓練** | 下記「3.3 復元訓練」を実施して記録を残す |
| シークレット期限の 1 か月前 | 認証シークレット更新 | [azure-deployment.md の運用メモ](azure-deployment.md#運用メモ) の手順で `AAD_CLIENT_SECRET` を更新 |

アプリは、バックアップから **7 日**（保存領域が未保護なら **3 日**）経つと起動時に
「最終バックアップから N 日経過しています」と表示します。表示されたら JSON を書き出してください。

## 3. バックアップと復元

### 3.1 バックアップ（両版共通）

1. ヘッダーの「データ ▾ → JSONを書き出す」
2. `<プロジェクト名>-<YYYY-MM-DD>.epcgraph.json` がダウンロードされる（タスク・依存・WBS 名称・カレンダー・ベースラインを含む完全な内容）
3. 端末の外（共有ドライブ等）へ保存する。ファイル名の日付で世代管理する

MS Project / Excel 連携用の「MS Project XML」「CSV」は**バックアップの代わりになりません**（一部の項目しか含まない）。

### 3.2 復元

1. 「データ ▾ → JSONを読み込む…」でバックアップファイルを選ぶ
2. **新しいプロジェクトとして**取り込まれる（既存プロジェクトは上書きされない）。サーバー版では読み込んだ人が所有者になる（1 ファイル 20MB まで）
3. 内容を確認したら、不要になった古いプロジェクトを「操作 ▾ → プロジェクトを削除…」で消す。サーバー版はメンバーを招待し直す

サーバー版で DB ごと戻す必要がある場合（誤削除が広範囲など）は Azure SQL のポイントインタイムリストア（7 日以内）を使う。
**別名の DB に復元して中身を確認してから**切り替えること（Azure ポータル → SQL データベース → 復元）。

### 3.3 復元訓練（四半期ごと）

1. 本番相当のプロジェクトを JSON で書き出す
2. 別ブラウザ（またはシークレットウィンドウ）で JSON を読み込む
3. タスク数・依存数・プロジェクト完了日・クリティカルパスが元と一致することを確認
4. サーバー版は加えて、Azure SQL を別名 DB へポイントインタイムリストアできることを確認し、確認後に削除
5. 実施日・所要時間・問題点を記録する

## 4. 障害対応

### 4.1 最初に確認すること

1. **どちらの版か**（URL が `github.io` ならローカル版、それ以外はサーバー版）
2. **影響範囲**（1 人だけか、全員か）。1 人だけなら端末・ブラウザ側を疑う
3. **いつから・何をした後か**（デプロイ直後なら直前のリリースを疑う → 4.4）

### 4.2 症状別の対処

| 症状 | 原因の候補 | 対処 |
|---|---|---|
| 「保存データの不整合を検出したため、…の履歴から復元しました」 | 保存データの破損（ブラウザ異常終了など） | 自動で直近の正常な履歴に戻っている。同時にダウンロードされた `…broken.epcgraph.json`（復元前のデータ）は保管し、直近の作業を目視で確認して不足分を入力し直す |
| 2 つ目のタブが「待機」表示のまま | 同じブラウザで別タブが開いている（ローカル版） | 先に開いたタブを閉じる。閉じると待機中のタブで編集できる |
| 保存バッジが「保存済み」にならない | 容量不足・ブラウザ設定でストレージ無効 | すぐ「JSONを書き出す」で退避。ブラウザの空き容量・プライベートモードでないかを確認 |
| 画面が真っ白・読み込みが終わらない | 古いキャッシュ・ブラウザ拡張 | 強制再読み込み（Ctrl+Shift+R）→ 別ブラウザで開く。ローカル版のデータは同じブラウザでしか見えない点に注意 |
| 「サーバーを起動しています…」が出る | DB の自動一時停止からの再開（サーバー版） | 正常。最大 1 分待つ。数分続く場合は 4.3 |
| 「ログインが必要です」・ログイン画面に戻る | セッション切れ | ログインし直す。続く場合は Entra ID の「割り当てが必要」設定と割り当てを確認 |
| 「閲覧権限のみのため保存できません」 | 閲覧者ロール | 所有者が「メンバー…」から編集者に変更。未保存の内容は `…unsaved.epcgraph.json` に自動退避済み |
| 「サーバーに保存できない内容でした」 | サーバー検証エラー（上限超過など） | 未保存分は `…unsaved.epcgraph.json` に退避済み。メッセージの項目を修正して入力し直す |
| 読み込み・保存で 413 | 1 リクエスト 20MB 超 | プロジェクトを分割する |

### 4.3 サーバー版の切り分け

1. `https://<ホスト名>/api/health` を開く（ログイン不要）
   - `{"ok":true}` → API は稼働。DB か認証、または利用者側の問題
   - 応答なし / 5xx → Functions の障害。Azure ポータル → Static Web Apps → 該当アプリの状態を確認
2. Application Insights → 「障害」で直近の例外とリクエストを確認（`alertEmails` 設定時は 5xx アラートも届く）
3. DB の状態（Azure ポータル → SQL データベース）: 一時停止中・容量上限・接続数を確認
4. 認証: Entra ID のアプリ登録のシークレット期限切れでないか（期限切れなら全員ログイン不可）

### 4.4 リリース起因が疑われるとき（ロールバック）

1. GitHub Actions で直前の成功したデプロイのコミットを確認
2. 問題のコミットを `git revert` して `main` に push（PR 経由）→ CI 成功後に自動で再デプロイ
3. データの形式（スキーマ）を変えるリリースの後は、ロールバック前に JSON を書き出しておく

## 5. リリース手順

1. PR を作成し、CI（Lint・単体テスト・本番ビルド・E2E（アクセシビリティ検査を含む）・E2E サーバーモード・API）が全て成功してからマージ
2. `main` へのマージで配信先へ自動デプロイ（配信先はリポジトリ変数で有効化。[配信先の設定](azure-deployment.md#配信先の設定検証--本番)）
3. デプロイ後の確認（5 分）
   - [ ] トップ（プロジェクト概要）が表示される
   - [ ] 依存関係・ガントチャート・タスク一覧が切り替えられる
   - [ ] タスクを 1 件編集し、保存バッジが「保存済み」になる（確認後に元へ戻す）
   - [ ] サーバー版: `/api/health` が `{"ok":true}`、ログイン中のアカウントが表示される
4. 問題があれば 4.4 でロールバック
